## Real bugs found (reproducible, reported, not fixed — test-specialist does not fix code)

1. **[MOST SEVERE, still open at end of pass] wp-admin's ordinary "Update" button silently deletes a reception's `_law_start`/`_law_end` postmeta, un-scheduling it.** Root cause precisely isolated: `functions/events/admin/event-screen.php` lines 441-445 unconditionally calls `law_event_apply_slot_label($post_id, $_POST['law_slot_label'] ?? '')` on every wp-admin save unless `$is_flagship` — no equivalent exclusion exists for receptions. Since a reception never has a slot label, `law_event_apply_slot_label()` (functions/events/settings.php:289-304) takes its `'' === $slot_label` branch and calls `law_event_update_meta(..., '_law_start', '')` / `'_law_end'`, which `law_event_update_meta()` (functions/events/meta.php:514-524) turns into a `delete_post_meta()` because the sanitized value is empty. Confirmed via direct network inspection (`request-body` showed the correct `law_start=2026-12-04T18:30` was actually POSTed — the bug is server-side, not a form issue) and reproduced cleanly twice (Wednesday and Friday receptions) by loading the edit screen and clicking Update with **zero** field changes. Impact: the reception vanishes from its calendar day tab and its own `/events/<slug>/` page 404s/redirects to the bare `/programme/` listing. The flagship event already has the identical, developer-acknowledged guard (`$is_flagship` exclusion, with a comment: "this screen must not write those keys for it: the slot select would blank its datetimes on the first Update") — receptions need the same treatment. I broke and then fully restored all three seeded receptions' `_law_start`/`_law_end` (plus Opening drinks' venue/price, which I'd also touched) via direct `wp post meta update` after confirming the bug — end state is clean, matches the task brief's documented fixture values.
2. **[Still open] 100%-discount reception bookings never send any confirmation email**, to attendee or committee, and never write the `_law_confirmation_sent` latch. Root cause: `law_reception_maybe_send_confirmation()` (functions/events/receptions.php:1203-1226) has a guard `if (!$force && '' === _law_stripe_invoice_url) return false;` intended to stop the email firing before Stripe's invoice is ready — but the free-booking call site (`law_reception_mark_paid($booking_id, array(), '', $user_id)`, ~line 899) never sets a Stripe invoice URL (there is no Stripe involvement at all for a 100%-off code) and never passes `$force = true`, so the guard silently blocks the email forever. Confirmed via Mailpit (no email appeared, waited and re-checked) and via postmeta (`_law_payment_status=paid` but no `_law_stripe_invoice_url`, no `_law_confirmation_sent` key at all on the booking). The paid path works correctly (webhook sets the invoice URL first, then the same function fires normally) — this is specific to the free/100%-code path.
3. **[Fixed live during this session, was open when first observed] Whole receptions committee dashboard (`/account/dashboard/receptions/`) rendered white-on-near-white — effectively invisible.** Root cause was two missing entries in per-template `is_page_template()` allow-lists: `functions/enqueue.php` (calendar.css) and `functions/events/submission-form.php` (event-form.css) both omitted `templates/account-dashboard-receptions.php`, so the page only loaded `law-admin.css`/`flagship-dashboard.css`/`law-modal.css` — none of which set the dark text colour that overrides the sitewide `body{color:#fff}` dark-hero default. Affected: page heading, intro paragraph, every table cell (Reception/Day/Venue/Places/Price/etc.), and the green "reception saved" success notice (rendered as a barely-visible pale strip). **This was fixed by someone else's concurrent commit while I was mid-pass** (`git log` gained 8 new "Receptions: ..." commits including "Receptions: the review findings..." partway through my session, in this shared working tree) — I re-verified after noticing and confirmed both lists now include the receptions template and the page renders correctly (dark navy text, visible green notice).
4. **Discount-code error message is invisible in the checkout modal.** Typing a bad code and pressing Apply DOES refuse it and DOES render "That discount code was not recognised." in the DOM, but the element uses class `law-form-notice is-error`, which resolves to `color:#fff` on `background:rgba(255,255,255,.12)` (event-form.css:270, written for the dark hero form) — invisible on the white `.law-modal__dialog`. The exact same category of bug was already fixed once in this file for a *different* class name: `law-modal.css:83-98` has a documented, deliberate light-mode override for `.law-modal .law-form-error` (with a comment explaining precisely this dark-on-light problem) but no equivalent override was added for `.law-modal .law-form-notice`. Also: the discount-code `<input>` itself is not visually marked invalid (plain grey border, no `aria-invalid`) when the code is rejected — brief expected "the field should be marked and a message shown." Net effect: a real user gets **zero visible feedback** on an invalid discount code beyond the total simply not changing. Confirmed not-a-duplicate of bug #3 — this is a different missing CSS rule, still open at end of pass (not touched by the concurrent commits).

## Process notes for next time

- **This was a genuinely, heavily shared working tree during the pass**: `git log` gained 8 new commits ("Receptions: the review findings...", etc.) and ~34 files were modified/untracked by the end, none of it mine. Two of the four bugs I initially found (the white-on-white CSS bug and the missing export trio) were **fixed/changed by that concurrent activity while I was still testing** — I caught this by noticing `git log` didn't match the session's start state, and re-verified both before finalizing the report. **Lesson: on a long pass on an actively-worked branch, re-check `git log`/`git status` partway through and re-verify any "still open" finding against current file state before writing the final report — don't trust an earlier observation as still true.**
- A second concurrent session/agent was also live-testing the exact same receptions during my pass (an unrelated "Denis Subscriber" booking #658 with the same RECEPTION25 code appeared in the bookings list and activity log that I didn't create) — expected noise per the shared-environment pattern, not a bug, didn't affect my results since bookings are independent rows.
- **Stripe's real hosted Checkout page needs a raw-coordinate `mousemove`+`mousedown`+`mouseup` click to expand the "Card" payment-method accordion**, not `click`/`eval .click()`, on this build — Playwright's semantic click kept reporting the invisible `AccordionButton-expandedClickArea` overlay as blocking/not-visible even though it's the real toggle. Coordinate click at the visible "Card" row worked immediately and revealed the Card number/Expiration/CVC/Cardholder/Billing-address fields (which ARE then reachable by normal `getByRole` fill). Reusable trick for any future Stripe checkout automation on this project.
- Registering fresh delegate accounts via `/register/` (no role field anymore — roles were retired sitewide per an earlier same-day commit) was faster and cleaner than hunting for existing attendee credentials; used `playwright-cli cookie-clear` to log out between identities and a second `-s=committee` session (playwright-cli's session flag) to hold the committee login and the delegate login simultaneously without cookie collisions.
- To capture what a genuinely white-on-white page actually contains (for diagnosis and for readable screenshots pre-fix), injected a temporary `<style>` tag forcing a dark color on the container via `page.evaluate` — clearly label these as debug-only screenshots, never conflate with the real (broken) rendering, which should also be screenshotted for the record.

Full persona walkthrough (new host registration + submission, committee review, returning host reply + edit) run against `http://localhost/law/` on 2026-09-04. See the conversation transcript for full screenshot list under `.playwright/screenshots/` (prefixed A-, B-, C-). Headline results:

**BLOCKER**: a genuine `events_committee` user has no findable path from the nav or `/account/` to the review queue at `/account/dashboard/`. Post-login they land on the host-oriented `/account/events/` ("My events" — "You have not submitted any events yet"), and the "Account" menu item goes to a page with zero body content for committee users. The dashboard itself (filters, search, per-event review panel, Approve/Send back/Reject, activity log, public-comment vs private-note distinction) is well built once you're on it. **Fix direction**: add a nav/account link to the review queue for `events_committee`, and/or redirect committee members to `/account/dashboard/` on login instead of `/account/events/`.

**FRICTION** (in rough priority order):
1. The "Information required" / clarification-needed email (sent on committee Send back) still has instructions written for the old Gravity Forms/GravityView UI: "Click Add comment... click Add to save... Click Submit to send your proposed event back." The real UI has one button, "Reply & resubmit to the committee," with clear helper text "Replying returns your event to the committee for review." Rewrite the email copy to match.
2. Saving edits to an already-approved/confirmed event (e.g. changing venue address, which IS still editable post-approval, correctly greyed-out vs editable field labelling elsewhere) redirects to `/account/events/` with **zero on-screen confirmation**, despite a `?law_notice=event-updated` query param that implies a banner was intended. Contrast with the dashboard's "Done: approve."/"Done: send back." and the reply flow's "Comment sent." — those all render correctly. Only the plain post-edit save on `/account/events/submit/` → redirect path is missing its notice text.
3. No self-serve withdraw/cancel for hosts, at any status (proposed or confirmed) — not a hard error, just absent, and the locked-fields banner doesn't point hosts anywhere (e.g. "contact the committee") as an alternative.
4. New-user registration sends no welcome/confirmation email to the registrant themselves — only an internal notification to admin addresses. First proposal-submission email onward does correctly email the submitter.
5. Logged-out visit to `/programme/` (and by extension single event/speaker pages) shows a bare "Sorry, but you do not have permission to view this content" with no link to log in/register — this is the pre-existing Members-plugin gating already tracked in [[known-issue-public-pages-members-gated]], re-confirmed still present.
6. Committee reviewers can't edit the event description inline from the review panel (by design — it's read-only there), but the only way to do so is the small "Full editing in wp-admin →" link with no framing text explaining that's the edit path.

**POLISH**: status-badge pill floats oddly isolated top-right on the committee review page; "Fee snapshot: £0.00" on a Proposed event with a non-zero fee tier selected could read as "this host isn't being charged" before it locks in on Approve; full-bleed cityscape hero image runs behind dense form sections (dietary/accessibility checkboxes) on register/submit pages; a host with 2+ Approved/Confirmed events in a year gets an automatic "Sponsored" badge (intentional parity with legacy `law_calendar_is_sponsored_event()`, in `functions/events/source.php`) which reads oddly for a repeat *paying* host, not just literal sponsors.

**Confirmed fixed**: [[known-issue-admin-post-blocks-non-admins]] no longer reproduces — see that memory file, updated same day.

**Operational note**: partway through this pass, screenshots named `D-*` began appearing in the shared `.playwright/screenshots/` folder that I did not create — timestamps interleaved with mine and the content showed my own in-progress test events, meaning a second concurrent playwright-cli session was running against the same live site/database at the same time (evidence of a parallel agent run, not mine). It didn't corrupt my results (every action in my own session produced the expected outcome end-to-end) but it's worth knowing that concurrent test-specialist runs share both the WordPress DB and the screenshots directory — collisions (login state, form races) are possible if two passes run at once.

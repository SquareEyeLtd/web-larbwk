Ran 2026-09-04 against http://localhost/law/ (law.localhost is stale per [[environment_url]]), branch events-4.1-rebuild-custom, commit 168f2bf.

**Real finding (Medium, unfixed as of this pass):** `templates/account-event-form.php` lines 13-20 load `$law_post = get_post($law_event_id)` and echo its title + workflow status (lines 49-57) BEFORE the `$law_can_edit` gate (line 64) blocks the rest of the form. Any authenticated user who can reach the submission form (event_host or sponsor — see `law_events_user_can_submit()`) can hit `/account/events/submit/?law_event=<any ID>` and read the title and status (Draft/Proposed/Sent back/Approved/Rejected/Confirmed) of ANY event, including other hosts' unsubmitted `law-draft` events. This directly violates the site-map guarantee that "`law-draft` events must be visible ONLY to their owner." No other event data leaks (description, speakers, fees etc. are correctly withheld — the block message replaces the rest of the form). Proof: created a `law-draft` post as another author via wp-cli, requested it as `claude-test-host`, got `BREAKER draft IDOR test — status: Draft` followed by "Sorry, you are not allowed to edit this event." Fix would be to null out `$law_post` (or skip the status line) whenever `$law_can_edit` is false. Test draft (post 2391) was deleted after confirming; no other cleanup needed for this finding.

**Correctly repelled (do not re-litigate unless code changes):**
- Registration (`law_register`): role escalation via forged `roles[]=administrator` — silently dropped, whitelist holds (`law_registration_roles()` intersect). Stored XSS in every text field — `sanitize_text_field`/`wp_kses_post` strip tags at both save and render (double-kses on `post_content`). SQLi via `'; DROP TABLE` in last_name — stored as inert literal text, prepared statements throughout. Honeypot bypass — filled field silently no-ops, no user created. Rate limit (20/hour/IP, keyed on `REMOTE_ADDR` not `X-Forwarded-For`) — kicks in reliably, XFF spoofing does nothing locally. Array-parameter pollution (`email[]=`) — no fatal, just fails `is_email()`. Duplicate email — blocked with a message (this IS a user-enumeration surface by necessity/design for registration forms; low severity, not flagging as a bug).
- Profile (`law_profile`): email change without `current_password` — blocked. Password change without `current_password` — blocked (verified old password still works, "new" password does not). CSRF with no nonce — 403 `check_admin_referer` failure. Role escalation via `roles[]=administrator/events_committee` — dropped (only self-service roles synced; admin/committee never touched by `law_registration_sync_roles()`). **Side-effect worth knowing, not a vuln:** submitting profile with a `roles[]` that omits your current self-service role (e.g. forgetting to tick "Event host") silently demotes you to `attendee` — by design (checkboxes reflect desired state), but no confirmation step. I accidentally demoted `claude-test-host` this way mid-test and restored it with `wp user set-role claude-test-host event_host` — role is back to `event_host`, confirmed.
- Event submission/edit (`law_event_form`): IDOR to EDIT another host's event (POST with someone else's `law_event_id` + your own valid nonce) — blocked with `wp_die` ("Sorry, you are not allowed to edit this event."), title unchanged in DB. Same for viewing the committee dashboard (`/account/dashboard/?event=<id>`) as a plain host — template shows "This dashboard is for the LAW committee." with zero event data leaked (unlike the form-page finding above). File upload MIME spoofing (GIF-with-embedded-PHP renamed `shell.jpg`, `Content-Type: image/jpeg`) — rejected by `wp_check_filetype_and_ext` real-content check ("must be a JPG, PNG or WebP image"), no file written, no post created (the bad-photo error blocks the whole save, not just the photo — minor UX-only gap: the template never calls the field-error helper for the dynamic `speaker_photo_{i}` key, so the host just sees a generic "fix the highlighted fields" with no visible reason — worth a product ticket, not a security issue).
- Comments/thread: cross-thread posting (reply to an event you don't own, valid nonce from your own event) — `wp_die` blocked. Stored XSS in comment body (`<script>`, `<img onerror>`) — `sanitize_textarea_field` strips all tags at save; rendered plain-text bubble confirmed in the actual thread HTML. Private committee notes and the full activity log (`LAW_EVENT_LOG_TYPE`) are structurally invisible to hosts — `parts/events/thread.php` only ever queries `LAW_EVENT_COMMENT_TYPE`, so there's no code path for a log/note leak into the host view, and a host has no way to write a log entry (`law_committee_action` handler is committee-gated and hosts never receive its nonce since the dashboard blocks rendering the form for them).
- Committee actions (approve/send back/reject, fee override, assignee): as a plain host, POST to `law_committee_action` with no nonce — 403. `law_user_is_committee()` gate is also checked in `law_event_workflow_transition()` itself (defence in depth even if the front controller were bypassed).
- Stripe webhook (`/wp-json/law/v1/stripe-webhook`): no `LAW_STRIPE_WEBHOOK_SECRET` configured locally by default → endpoint fails closed on every request (400 "Webhook secret is not configured"), so no forged-webhook bypass is even reachable out of the box. Temporarily defined a test secret in wp-config.php to check the verifier logic itself, then reverted it (config now back to the commented-out placeholder, confirmed): wrong-secret signature → 400 rejected; stale timestamp (>300s) → 400 rejected; valid signature → accepted and processed correctly including a real amount-mismatch alert email (`admin_stripe_error`) when the fake `amount_paid` didn't match the fee snapshot; replayed event ID → `{"duplicate":true}`, no double-processing. `hash_equals()` is used for the HMAC compare (timing-safe). This is all correct; a real attacker without the webhook secret cannot forge events. Test artifacts (3 log entries on fixture event 1224 from the valid-signature test, and one processed-event-ID `evt_breaker_test_1` in the `law_stripe_processed_events` option) were cleaned up except the harmless processed-ID cache entry, which is bounded/rotating and not worth touching.
- REST API: `wp-json/wp/v2/law_event` and `/law_speaker` both 404 — `show_in_rest => false` holds, confirmed empty from `/wp-json/wp/v2/types`.
- Direct front-end access to non-`publish` events (`?post_type=law_event&p=<id>` for draft/proposed/sent-back/approved fixtures) while logged out — all 404. Legacy `?event=` redirect only fires for `publish` status.
- Auth (`functions/auth.php`): forgot-password gives an identical neutral "if that email has an account…" response whether or not the account exists (no enumeration there — contrast with registration's necessary duplicate-email message above). Reset link re-validates the key server-side on POST, not just on the GET render. Redirects go through `wp_validate_redirect()` (no open redirect via `redirect_to`).

Test accounts used: `claude-test-host` (event_host, ID 389, owns 1224 + 2388) — role was temporarily knocked to `attendee` mid-test by my own profile-form probing and has been restored. No other fixture data was permanently altered. See [[test-accounts]] for credentials.

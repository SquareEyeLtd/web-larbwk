**Validation states — mostly PASS, one real bug found.**
- Plain `<input>` invalid/cleared cycle is correct on BOTH palettes (verified with an injected `.is-invalid`/`.law-form-error` DOM state, since actually triggering server-side validation errors would mean creating real test submissions on host's live account — cheaper and equally valid to test the stylesheet's own class contract directly):
  - Dark: invalid = `2px solid rgb(255,92,77)` (`#ff5c4d`); touched/cleared = `2px solid rgba(0,0,0,0)` (transparent, width held at 2px, box-sizing keeps the rendered width identical — no text shift). Screenshots `17-dark-title-invalid.png`.
  - Light: invalid = `2px solid rgb(179,45,46)` (`#b32d2e`); touched/cleared = `1px solid rgb(200,200,212)` (back to the resting grey border, again no shift). Screenshot `18-light-title-invalid.png`.
  - Error message strip on the dark form: white text, `rgba(255,255,255,.12)` bg, `#ff5c4d` left rule — matches spec (`16-dark-form-description-error.png`).
- **BUG (real, but likely pre-existing, not introduced by this diff):** the required-Description TinyMCE box's invalid border computes to **1px**, not the 2px both `rich-text.css` and the task spec call for — on EVERY palette (checked on the host's dark form and the committee's light form, both the main Description field and speaker Biography). Root cause: TinyMCE's own init/skin JS sets an inline `style="border-width: 1px"` directly on `.mce-tinymce`, and a plain (non-`!important`) inline style beats any external-stylesheet declaration for that one CSS property, so `rich-text.css`'s `.law-form-field.is-invalid .law-rich-text .mce-tinymce { border: 2px solid var(--law-form-error-accent, #ff5c4d) }` only wins the colour component, not the width. The border colour IS correct (`#ff5c4d` dark / `#b32d2e` light); only the width is wrong. Confirmed via `getComputedStyle(...).borderTopWidth` etc, all 4 sides uniformly 1px, both before and after simulating `.is-invalid`. This predates the refactor — the rule's `2px` value is untouched by the diff, only its colour argument changed from a literal hex to `var(..., fallback)` — so it is NOT a regression from this specific CSS-custom-property change, but it IS a genuine, verifiable deviation from the documented/intended validation styling and should be fixed (e.g. rich-text.css or law-rich-text.js needs `!important` on the invalid rule's border-width, or the JS needs to stop hardcoding `border-width` inline once wp.editor has initialised).

**Pre-existing (non-regression) contrast oddity spotted incidentally:** `.law-form-hint` paragraphs inside the dark hero form's "Speakers"/"Owners & contacts" section intros compute plain white (`rgb(255,255,255)`), not the pale-lilac `#d7d7ea` the token defines — `auth.css`'s `.auth-hero .auth-intro p { color: #fff }` (specificity 0,2,1) beats `.law-form-hint` (0,1,0) wherever both wrap the same `<p>`. Confirmed `auth.css` is untouched in this diff and the specificity relationship was identical before the refactor (old rule was the same single-class selector), so this is not something the refactor caused. Not a legibility problem (white on the purple hero reads fine) — just not the exact token colour. Flagging because it's visible on the screen under test, not asking for a fix.

**Validation states — mostly PASS, one real bug found.**
- Plain `<input>` invalid/cleared cycle is correct on BOTH palettes (verified with an injected `.is-invalid`/`.law-form-error` DOM state, since actually triggering server-side validation errors would mean creating real test submissions on host's live account — cheaper and equally valid to test the stylesheet's own class contract directly):
  - Dark: invalid = `2px solid rgb(255,92,77)` (`#ff5c4d`); touched/cleared = `2px solid rgba(0,0,0,0)` (transparent, width held at 2px, box-sizing keeps the rendered width identical — no text shift). Screenshots `17-dark-title-invalid.png`.
  - Light: invalid = `2px solid rgb(179,45,46)` (`#b32d2e`); touched/cleared = `1px solid rgb(200,200,212)` (back to the resting grey border, again no shift). Screenshot `18-light-title-invalid.png`.
  - Error message strip on the dark form: white text, `rgba(255,255,255,.12)` bg, `#ff5c4d` left rule — matches spec (`16-dark-form-description-error.png`).
- **BUG (real, but likely pre-existing, not introduced by this diff):** the required-Description TinyMCE box's invalid border computes to **1px**, not the 2px both `rich-text.css` and the task spec call for — on EVERY palette (checked on the host's dark form and the committee's light form, both the main Description field and speaker Biography). Root cause: TinyMCE's own init/skin JS sets an inline `style="border-width: 1px"` directly on `.mce-tinymce`, and a plain (non-`!important`) inline style beats any external-stylesheet declaration for that one CSS property, so `rich-text.css`'s `.law-form-field.is-invalid .law-rich-text .mce-tinymce { border: 2px solid var(--law-form-error-accent, #ff5c4d) }` only wins the colour component, not the width. The border colour IS correct (`#ff5c4d` dark / `#b32d2e` light); only the width is wrong. Confirmed via `getComputedStyle(...).borderTopWidth` etc, all 4 sides uniformly 1px, both before and after simulating `.is-invalid`. This predates the refactor — the rule's `2px` value is untouched by the diff, only its colour argument changed from a literal hex to `var(..., fallback)` — so it is NOT a regression from this specific CSS-custom-property change, but it IS a genuine, verifiable deviation from the documented/intended validation styling and should be fixed (e.g. rich-text.css or law-rich-text.js needs `!important` on the invalid rule's border-width, or the JS needs to stop hardcoding `border-width` inline once wp.editor has initialised).

**Pre-existing (non-regression) contrast oddity spotted incidentally:** `.law-form-hint` paragraphs inside the dark hero form's "Speakers"/"Owners & contacts" section intros compute plain white (`rgb(255,255,255)`), not the pale-lilac `#d7d7ea` the token defines — `auth.css`'s `.auth-hero .auth-intro p { color: #fff }` (specificity 0,2,1) beats `.law-form-hint` (0,1,0) wherever both wrap the same `<p>`. Confirmed `auth.css` is untouched in this diff and the specificity relationship was identical before the refactor (old rule was the same single-class selector), so this is not something the refactor caused. Not a legibility problem (white on the purple hero reads fine) — just not the exact token colour. Flagging because it's visible on the screen under test, not asking for a fix.

**UPDATE (same day, retest after coordinator's rich-text.css patch):** Denis pushed two changes to `assets/css/rich-text.css` (added `.law-rich-text.is-invalid .mce-tinymce` to the invalid-border selector, and `.law-rich-text > .law-form-error[data-law-rich-error]` to the block-display rule) and corrected my root-cause diagnosis. Retested with `getComputedStyle`, not impressions.

- **The structural diagnosis was right and the fix works.** In a repeater row (`.law-row > .law-row-grid > .law-row-wide > span.law-rich-text > textarea`) there genuinely is no `.law-form-field` ancestor — confirmed via `.closest('.law-form-field')` returning null for both the session Description and speaker Biography rows. Before the patch, `is-invalid` there had no selector to land on. After the patch, simulating the exact DOM state `law-rich-text.js`'s private `showError()` produces (`is-invalid` on `.law-rich-text`, plus an appended `<span class="law-form-error" role="alert" data-law-rich-error>` inside it) gives the correct `border-color: rgb(179,45,46)` (light) and the message computes `display: block` in both rows. Screenshot `20-retest-A-speaker-bio-invalid.png`.
- **But my width claim was also right, and is still real after the patch.** `getComputedStyle(...).borderTopWidth` (all 4 sides checked individually) is **1px, not 2px**, on every rich-text box tested post-patch: the standalone host-form Description (genuine client-side validation this time, real "Submit event" click, no DOM simulation — screenshot `19-retest-B-host-description-invalid.png`), both repeater rows above, and a wp-admin speaker Biography editor (`21-retest-D-wpadmin-speaker-bio.png`, fallback `#ff5c4d` confirmed correct there too, no `event-form.css` token in scope). Proof of mechanism, not assumption: `document.querySelector('.mce-tinymce').getAttribute('style')` returns literally `"visibility: hidden; border-width: 1px; width: 100%;"` on every instance — a real inline style, not a stylesheet artifact. Calling `.style.removeProperty('border-width')` makes the computed width jump to 2px **immediately** and it is never reapplied — proving TinyMCE's own JS wrote it once at init and the stylesheet rule underneath is correct. Pushed back on the coordinator's claim that this can't happen per-property: it's standard CSS cascade (an inline `style` attribute is a higher-precedence origin than any non-`!important` external rule, applied per longhand, not per matched declaration block) — verifiable in any devtools "Computed" panel. Also found the literal string `"border-width"` once in `wp-includes/js/tinymce/tinymce.min.js` (the coordinator had grepped for camelCase `borderWidth` and found nothing) inside what looks like a generic style parse/serialize helper — flagged as a lead, not a confirmed call site; minified code wasn't worth fully tracing given the DOM evidence already proves the mechanism unambiguously. Net: real, reproducible, NOT fixed by the coordinator's patch (their patch didn't touch the width value and couldn't have), and not caused by the original event-form.css token refactor either — a third, independent layer of the same border. Fix needs `!important` on the width (or the two longhands split so width isn't in a shorthand competing with the inline one), or the JS to stop hardcoding it.
- **Found a third, deeper issue while chasing this, upstream of any CSS:** the session Description and speaker Biography fields can **never actually reach `is-invalid` via real user action today**, patch or no patch. `law_rich_text_field()` is called for both in `parts/events/event-form-fields.php` (~line 224 speakers, ~line 455 sessions) **without** a `'required'` argument, so neither textarea ever gets `data-law-rich-required` — and `law-rich-text.js`'s client-side `validate()` only walks `textarea[data-law-rich][data-law-rich-required]`, so it never calls `showError()` for either field, so `is-invalid` never lands on `.law-rich-text` for them by itself. Confirmed on the committee "Save changes" flow with a real server round trip (emptied a session's Description, filled everything else, submitted): the response has **zero** `.is-invalid` elements anywhere on the page; the only sign of the error is one generic top-of-repeater notice, "Each session needs a description. Please complete row 1, or clear it." (`law_events_form_save()`'s `$row_rules` in `functions/events/submission-form.php` ~line 326, keyed by group not by row/field). Separately, speaker Biography isn't in any required-fields list at all (`$row_rules['speakers']` only requires first_name/last_name/email/organisation/job_title) — its label has no asterisk, and it is not just currently unreachable but can never be "invalid" under current business rules. So the coordinator's new CSS selector is correct and does what it says, but for these two specific fields it's presently dead code (same category as the `.law-row.is-invalid` selector they already flagged as dead) — the gap is in the PHP form-field definitions, not in rich-text.css.

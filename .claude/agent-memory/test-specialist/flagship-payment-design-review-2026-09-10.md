Full pass across all 7 views Denis asked for (public page logged out/in, apply modal + no-JS fallback, Stripe redirect, committee `/account/dashboard/flagship-bookings/`, `/account/dashboard/discounts/`, attendee `/account/bookings/` + manage view, `/account/dashboard/flagship/` pricing fieldset, wp-admin booking screen). Backend smoke clean (`php -l` on all uncommitted/new PHP, homepage 200, no "critical error", full PHPUnit suite 68/68 green including FlagshipPaymentsTest/DiscountsTest/FlagshipBookingsDashboardTest/WebhookTest). Registered a real attendee via `/register/`, drove a real application through to the Stripe hosted checkout redirect (confirmed correct: test-mode "Sandbox" tag, LAW branding, email prefilled, SetupIntent-style "save card, don't charge yet" page matching the modal's copy), stopped there per instructions.

**Real bug 1 (should fix, likely Medium/legal): the attendee consent checkbox "I accept the registration terms and conditions" links to `/policies/event-host-terms-conditions/`**, whose actual content is 100% about hosting a satellite event (venue arranging, "£1,200 or £600 + VAT" host ticket price, "event proposer" language) — nothing about attending the flagship conference. Root cause: `law_events_terms_url()` in `functions/events/settings.php` was written for the host submission form (form 2 field 69 parity target) and is now reused as-is by `parts/events/flagship-apply-modal.php:231` for the attendee flow. Needs either its own attendee-facing terms page/setting, or at minimum a generic fallback that isn't host-specific.

**Real bug 2 (Low/Medium, cosmetic but sloppy): the flagship application's own manage view (`/account/bookings/?law_booking=<id>`) renders two identical "Back to my bookings" links stacked directly on top of each other.** `templates/account-bookings.php` lines 37-48 renders one unconditionally whenever `?law_booking` + CPT mode, then delegates to `parts/events/booking-manage.php` → `parts/events/flagship-manage-application.php`, which renders its own back-link again at lines 49-58. Fix: drop one (cleanest is removing the inner one in flagship-manage-application.php since the outer template already covers every `?law_booking` view including hosted bookings).

**Minor/informational, not unique to this build**: the sitewide brand orange `#ef7d05` with white button text (used on "Update payment method", "Apply", "Add attendee", etc.) computes to ~2.76:1 contrast at the ~12.8px/600-weight button size used everywhere — fails WCAG AA (needs 4.5:1, or 3:1 even at "large text" size, which this isn't). This is an established sitewide design-system colour (also in `auth.css`, `event-form.css`), not something the flagship feature introduced, but every new CTA button in this build inherits it.

**Minor doc nit**: `assets/css/calendar.css` around line 970 has a code comment claiming the `--applied`/waitlist-shared amber badge (`#a35300` on `#fdeee0`) is "about 5.6:1" contrast; actual computed value is ~4.87:1 (still passes AA, comment is just off). The neighbouring `--payment-failed` badge's claimed 6.4:1 is spot-on when independently computed. Both are genuinely well-considered, documented colour decisions (rare to see contrast math in a CSS comment) — worth noting as a good pattern, just flag the one number.

**Confirmed NOT bugs (investigated, ruled out)**: (1) the apply modal's "cut off" appearance in a `--full-page` Playwright screenshot is a `position: fixed` + full-page-screenshot artifact, not real — the actual dialog (`.law-modal__dialog--wide`) has proper `overflow-y: auto` and is fully reachable by scrolling. (2) `document.body.scrollWidth` / `documentElement.scrollWidth` reporting far wider than the viewport (both on the flagship-bookings table at 1440 and at mobile 390) is the same kind of false positive — content clipped inside a nested `overflow-x: auto` container (`.law-dashboard__table-wrap`) still gets counted toward the document's reported scrollWidth in this Chromium build, but `window.scrollX` never moves and no unclipped element actually exceeds the viewport when ancestor-clipping is accounted for. **Lesson for next pass: don't trust bare `body.scrollWidth` vs `clientWidth` as a page-horizontal-scroll check on this project when a scrollable table is on the page — verify with `window.scrollTo()` + read back `window.scrollX`, or walk the DOM excluding descendants of any `overflow-x: auto/hidden/scroll` ancestor.** (3) the flagship dashboard's price-preview line ("Delegates pay £X until...") does not update live on keystroke — confirmed it's server-rendered from saved settings with no JS listener, which is a fine design, just not literally "live" in the reactive sense.

**Design/UX highlights worth repeating elsewhere**: the Approve/Decline confirm dialogs on the committee bookings dashboard are excellent models — specific consequences spelled out ("This charges £660.00 to the card... They are emailed a confirmation with a VAT invoice and a calendar invitation"), button labels state the exact amount rather than "OK"/"Confirm". The failed-payment red panel on the attendee's own booking view is equally good (explains the place is still held, gives a fix-by date, has a clear "Update payment method" CTA). The `decidable` gating (no Approve/Decline shown until a card is actually confirmed saved, even though the row is visible under the "Awaiting card details" filter) is a deliberate, comment-documented design choice, not a bug — don't re-flag it.

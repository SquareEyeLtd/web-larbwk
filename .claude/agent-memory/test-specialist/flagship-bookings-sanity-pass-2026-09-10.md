Follow-up to [[flagship-payment-design-review-2026-09-10]], same day, focused on the committee bookings table redesign, discount codes, and account menu reorder. Backend smoke clean (php -l on all 35 changed/9 new PHP files, homepage 200, no critical error).

**Everything in the brief passed.** Notably:
- Declined badge tooltip: confirmed via DOM (`title="Just because"` on `.law-cal-card__badge--cancelled`), no reason text printed beneath it.
- Bulk approve/decline links: `disabled`/`aria-disabled` toggle correctly on row-checkbox tick/untick and on select-all, including after an AJAX filter swap (delegated handlers survive re-render, confirmed by re-testing tick-to-enable and the modal opener post-swap).
- All 5 modals (per-row approve, per-row decline, bulk approve, bulk decline, add-attendee-without-payment) are genuinely left-aligned throughout (title/copy/field labels/help text) — the text-align regression mentioned in the brief is NOT present.
- AJAX filter swap confirmed via a `beforeunload`-flag probe (`window.__navFlag` surviving the filter change) rather than trusting the URL bar, since this app uses `history.pushState` on filter change so the URL alone doesn't prove no reload happened. **Reusable technique for this project**: set a flag + `beforeunload` listener before triggering a suspected-AJAX action, then read the flag back — a real navigation clears it, pushState does not.
- Discount codes: "Add a code" is a normal button (not full width); `starts`/`expires` are real `type="datetime-local"`, `value` (Amount) is `type="number"`; created a code with both dates, reopened it for edit, both came back populated correctly (`2026-09-10T09:00` / `2026-09-20T17:30`) — the YYYY-MM-DDTHH:MM empty-render risk named in the brief did not manifest. No "Delete" control exists in the UI, only Disable/Enable — used Disable to clean up per the task's own allowance, left as `post_status=draft`.
- Account dropdown order matches spec exactly for committee; "Manage bookings" is gone, replaced by "Hosted bookings".
- Public flagship page and apply-modal copy: "our payment provider, Stripe, where you choose how you would like to pay" / "saved but NOT charged" — correctly payment-method-agnostic, no card assumption.
- Delegate's own booking view: "Payment method" row (not "Card") reads "Visa ending 4242, expires 12/2029" as required.

**No column is wider than 12rem — investigate before flagging.** Measured `<th>` rendered widths at 1440px and got ~15.93rem for Applicant/Email/Payment, which looks like a violation at first glance. It isn't: `assets/css/calendar.css` ~line 1841 has a comment-documented, deliberate design ("No column wider than 12rem (Denis, 10 September 2026)") explaining the table is `auto-layout`, so `max-width: 12rem` caps what a column *asks* for, not an absolute ceiling — spare viewport width can still be handed to a column. The actual guarantee is that long content *wraps* (`white-space: normal; overflow-wrap: break-word`) instead of stretching the table, which was independently confirmed at 900px (email wrapped to two lines, table stayed within its wrapper). **Lesson: for this table, check wrapping behavior with long content, not raw computed column width, when verifying the "12rem" rule.**

**Attendee terms link (real bug found in [[flagship-payment-design-review-2026-09-10]] this morning) has been deliberately, visibly fixed, not just patched over**: `functions/events/settings.php` now has a dedicated `law_events_attendee_terms_url()` (distinct from the host-facing `law_events_terms_url()`), falling back to `/policies/` instead of the host terms page, with a documented rationale in the code comment and a `law_events_attendee_terms_configured()` helper that shows a **"Not set" warning directly in the wp-admin LAW Settings screen** (`law-attendee-terms` field) when no real attendee terms page/URL has been configured. The live fallback target `/policies/` is currently a genuinely empty page (title only, no body content) — so an attendee clicking the link today still lands somewhere unhelpful, but this is a known, surfaced, one-field admin configuration gap (not a code defect), and Denis needs to either write `/policies/` content or set `attendee_terms_page` in LAW Settings to a real page/URL.

**Decidable-row testing required temporarily flipping real data.** No booking was in an "Awaiting review + card saved" state among the 3 real applications (#649/#650 confirmed & paid, #651 declined) — all pre-decided, so nothing rendered in the per-row/bulk action columns by default. To verify the Approve/Decline link layout, `wp db query`'d `wp_posts.post_status` on booking #651 (post ID 127151) from `law-declined` to `law-applied` and back twice (each time verified reverted before moving on) — a direct SQL status flip has no Stripe/email side effects (unlike clicking the real Approve/Decline actions), and `_law_decline_reason` postmeta is stored separately from `post_status` so it survived intact. Confirmed final state is back to `law-declined` at the end of the pass.

**Committee test account (`claude-test-committee`) had a blank profile (no first/last name/country)**, which meant the flagship page's "Apply" button first showed an unrelated **profile-completion gate modal** ("Apply to attend... please add your first name and surname to your profile") instead of the real payment-consent apply modal. Had to fill in First name, Last name AND Country of residence (all three are required; country is easy to miss since it's a `<select>` defaulting to "Select country") via `/account/profile/` before the real apply modal would render. This profile completion is now a **persisted change** to the shared `claude-test-committee` test account (name "Claude Committee", country United Kingdom) — a reasonable one-time fix that unblocks this flow for future passes, not reverted.

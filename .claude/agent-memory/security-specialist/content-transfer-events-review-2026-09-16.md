Reviewed `functions/events/migration/content-transfer.php` (format version 3, the `events` bundle key added 16 September 2026) against `tests/ContentTransferTest.php`. Two real findings, reported to the orchestrator, not yet fixed as of this review:

**P0 — status-guard bypass via the bundle's `external` claim, not the post's real classification.** `law_content_transfer_write_event()` computes `$managed = $external && ! $creating && in_array($status, ['publish','law-draft'])` using `$external` = the BUNDLE's top-level `event['external']` boolean (fully attacker-controlled), not the target post's actual stored `_law_is_external` meta. The `wp_insert_post_data` guard in `workflow.php` (~line 112) correctly checks the REAL, currently-stored `_law_is_external` via `law_event_is_managed_by_law()`, so a single import run can't push a status write through on a genuinely-hosted event (guard reverts it). BUT `_law_is_external` is itself in the generic meta allow-list (`law_content_transfer_event_meta_keys()`, line 544) and gets written unconditionally by the same call, AFTER the guarded `wp_update_post()`. So: run 1 on an existing hosted event with bundle `external: true` + `meta._law_is_external: 1` + `status: publish` — status write is blocked (guard sees old meta = hosted), but `_law_is_external` is persisted as 1 regardless. Run 2 of the same (or any) bundle against the same event — the guard now sees real `_law_is_external = 1`, exemption fires, `post_status` goes straight to `publish`, skipping the whole approval workflow (no fee snapshot, no Stripe invoice, no co-owner accounts, no host email). Re-running an import is the tool's own normal/idempotent usage pattern, not an edge case. The preview has the identical bug independently: `law_content_transfer_event_after()` (~line 2906) and `law_content_transfer_event_status_notes()` (~line 2976, the `if ($external || ...) return array();` line ~2993) both branch on the bundle's `$external` claim too, so the dry-run preview *also* wrongly predicts/suppresses-the-warning-for a status change that the real single-run apply will NOT make — a "preview promises something the apply doesn't do" bug riding the same root cause.
Fix: compute the managed/exemption eligibility (and the preview's prediction) from the post's PRE-EXISTING stored `_law_is_external` (or `law_event_is_managed_by_law($event_id)` read before any write in this run), never from the bundle's own claim. Consider also treating `_law_is_external` as immutable-after-creation for an existing event (only settable on `$creating`), matching how the real `law_external_event_save()` treats classification as fixed at creation.

**P1 — event ownership hijack via `owner_email` / co-owner rows on an EXISTING event.** `law_content_transfer_write_event()` sets `$post['post_author'] = (int) $values['owner_id']` unconditionally (line ~2742, not gated to `$creating`), and separately `law_content_transfer_link_co_owners()` (added between my two reads of the file, ~line 2697) links `_law_co_owner_ids` to any existing account resolved by email in `_law_co_owner_rows`. `law_content_transfer_resolve_user()` only matches an EXISTING account by `get_user_by('email')` — never creates one, so no user-enumeration/account-creation issue — but a bundle naming a real, known email address of ANY existing WP user (found via a matched `gf_entry_id`/slug row for an event that already has a legitimate different owner) silently reassigns `post_author` (or adds a co-owner) to that unrelated account. Since `law_user_can_manage_event()` treats author and co-owners identically to committee, this grants that third party full edit/view rights over the event, including private fields surfaced in the event's own activity log entry this same import writes (`_law_invoice_email`, `_law_invoice_address`, `_law_vat_number`, rejection/cancellation reasons are all in `law_content_transfer_event_labels()`'s diff). Same root shape as the already-known co-owner/speaker email-match auto-link anti-pattern (see [[recurring-patterns]]), newly reachable through the admin-only bundle-import surface rather than only a logged-in host's own form.
Fix: either require an explicit consent/notification step before reassigning `post_author` on an EXISTING event (only trust `owner_id` at `$creating`, same restriction the P0 fix would apply to `_law_is_external`), or leave an existing event's author/co-owners untouched by import entirely and only report a mismatch, mirroring how the file already treats workflow status as reported-not-written.

**Confirmed clean in this review, don't re-litigate:**
- `law_content_transfer_find_event()` correctly constrained to `LAW_EVENT_CPT` on both the `gf_entry_id` meta query and `get_page_by_path()`; reception/flagship rows are refused before reaching the generic writer.
- `law_content_transfer_resolve_user()` never creates an account (confirmed no `wp_insert_user`/`wp_create_user` anywhere in this file).
- `_law_assignee` reassignment is safe even though resolved the same way as owner: `law_event_update_meta()` re-runs the value through the schema sanitiser (`law_events_sanitize_assignee()` in capabilities.php), which silently drops any user ID lacking `edit_others_law_events` — so only genuinely committee-capable accounts can ever end up as assignee via a bundle.
- `law_flagship_save_sessions()`'s orphan-deletion is scoped to `array_diff($owned, $kept)` where `$owned = law_event_session_ids($event_id)` — cannot reach another event's sessions.
- Speaker rows always carry `speaker_id => 0` / `is_new => true` (hardcoded in `law_content_transfer_event_speaker_input()`), so no speaker_id from the file is ever honoured directly — only the pre-existing email/name-match backfill in `law_speaker_upsert()` applies (known, separately-tracked P2 pattern).
- Organisation slugs resolved via `get_page_by_path($slug, OBJECT, 'organisation')`, correctly type-scoped.
- Zip handling: path traversal closed by an allowlist (`law_content_transfer_safe_entry()`, both at read time and again at use time via `law_content_transfer_archive_file()`), zip-bomb guard reads the declared uncompressed size from the directory before writing anything, image count capped at 400, upload capped at 64MB. All confirmed sound.
- Image fetch (version-1/no-archive fallback) restricted to the bundle's own declared `uploads_baseurl` prefix, going through `wp_safe_remote_get()`/`download_url()`; bytes always re-validated via `wp_check_filetype_and_ext()` regardless of route (zip-carried or fetched), never trusting the claimed filename/MIME.
- Admin panel (`law_content_transfer_panel()`): `current_user_can('manage_options')` + `check_admin_referer()` gate both preview and apply POSTs; results table (`ref`, `changes`) rendered with `esc_html()` throughout — no XSS.
- No hardcoded secrets in the file.
- Export allow-list (`law_content_transfer_event_meta_keys()`) correctly excludes all Stripe/payment/fee-snapshot/capacity-latch/co-owner-ID/reference/gf-entry-id keys per the file's own documented rationale — verified against the actual list, not just the comment.

**Re-verification, same day, after the coordinator's fix pass:** re-read the file fresh (it had moved again — `law_content_transfer_link_co_owners()` and session GF-entry-ID restamping were added between my two original reads). Confirmed:
- P0 genuinely closed, both halves independently sufficient: `run_event()` now reassigns `$external` from `get_post_meta($event_id, '_law_is_external', true)` before any write (only trusting the bundle's claim on `$creating`), and that corrected value flows into `write_event()`, `event_after()` and `event_status_notes()` alike, so the preview can no longer promise a status change the apply refuses. Independently, `write_event()`'s meta loop now `continue`s on `_law_is_external` whenever `! $creating`, so the flag that unlocks the guard's exemption can never be written onto an existing event by import at all — closing the two-run bypass at the root, not just at the symptom. `_law_is_flagship`/`_law_is_reception` were never in the allow-list to begin with (confirmed by re-reading the actual array, not just the docblock), so `law_event_is_managed_by_law()` cannot be tricked into "yes" via those either. `try/finally` around `wp_update_post()` closes the global-flag-survives-an-exception concern. Grepped the whole file for `post_status` writes: only the creation insert (intentionally unrestricted, matches documented design) and the now-fixed `$managed` block remain — no other route.
- P1 (owner) genuinely closed: `post_author` is set only when `$creating`; an existing-event mismatch produces an "Owner left alone" note instead of a silent write, and `event_after()` mirrors the same restriction so the preview doesn't promise it either.
- **Pushed back on the co-owner half or the P1 fix**, which the coordinator deliberately left open: `law_content_transfer_link_co_owners()` still links `_law_co_owner_ids` unconditionally (not gated on `$creating`), and `law_user_can_manage_event()` grants a co-owner the exact same access as the author (capabilities.php:83-86) — the coordinator's own stated reasoning for restricting `post_author` ("ownership is who can open the event... includes the invoicing contact and address this same run writes") applies verbatim to co-owners and wasn't applied there. Their three counter-arguments don't hold up: (1) the rows traveling is fine, but that's a different act from the automatic LINKING, same distinction they already drew for owner; (2) "only links addresses that already have an account" was never the mitigating factor for the owner case either — it's still an unconsented grant to a real, unrelated account; (3) "approving would link the same people anyway" is only true for an event that hasn't been approved yet — for an ALREADY-approved/confirmed/live event, `law_event_ensure_co_owner_users()` never runs again, so import-time linking is the ONLY thing that grants access, with no future human decision point at all; and even pre-approval, "it'll happen anyway at approval" isn't a reason to skip the human review approval represents. Also factually: there's no note generated for the case that actually matters (a row DOES resolve to an existing account) — only for the unresolved case — so "every change is named in the preview" is true for rows-as-text but not for the access grant itself. Recommended restricting co-owner linking to `$creating` too, same shape as owner.
- P2 row cap: `LAW_CONTENT_TRANSFER_MAX_ROWS` (2000, checked in `law_content_transfer_parse()`, refuses rather than truncates) correctly bounds the four TOP-LEVEL lists (`receptions`, `events`, `discounts`, `emails`). It does NOT bound nested repeaters — sessions-per-event or speakers-per-session/event are uncapped, so a bundle with few top-level events but very large nested session/speaker arrays (cheap per-row in JSON bytes) could still drive a large synchronous run within the 64MB cap. Flagged as a residual gap, not re-opening the P2 as failed but noting the cap doesn't fully cover what "no row-count limit" originally meant. No filter on the constant is fine and consistent with `MAX_IMAGES`/`MAX_BYTES` (also unfiltered); only `MAX_UNZIPPED` is filterable, for testability, not consistency.
- No new issues introduced by the three fixes, beyond one cosmetic (non-security) inconsistency: `$ref` (used in `law_migration_log()` messages) is still built from the bundle's ORIGINAL claimed `external` before the correction, while `$row['kind']` (shown in the results table) now uses the corrected value — so a misclassified row's log line and table row can disagree on "external event"/"hosted event" labelling. Cosmetic only, not worth a numbered finding.

**Lower-severity notes given, not separately numbered as blocking:**
- P2: no cap on the NUMBER of rows in `bundle['events']`/`receptions`/`discounts`/`emails` — only the 64MB overall upload size and the 400-image cap bound things. A synthetic bundle with tens of thousands of minimal event rows runs synchronously inside one admin-post request (unlike the module's own batched AJAX migration runner) and could hit PHP max_execution_time/memory. Worth a row-count cap or routing through the batched runner.
- P2: the extracted-image working directory (`wp-content/uploads/law-migration/ct-*/`) has `.htaccess` + `index.php` only, no runtime self-test unlike the DB-snapshot exposure gate in `migration/runner.php` (which the phase-B review confirmed has a live unauthenticated-GET self-test). Lower stakes (speaker photos, not a DB dump) and the file's own comment concedes this, but genuinely weaker than the sibling gate on an nginx host.

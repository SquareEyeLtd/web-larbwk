On 2026-09-04, as the third of three adversarial test personas, ran a full attack-surface sweep of `functions/events/` on branch `events-4.1-rebuild-custom` (after commit 168f2bf): capabilities.php, workflow.php, submission-form.php, comments.php, committee.php, co-owners.php, meta.php, fees.php, stripe/{client,service,webhook}.php, migration/{page,report,runner}.php, admin/{event,speaker,session}-screen.php, admin/emails-screen.php, post-types.php, statuses.php, source.php, registration.php, plus `functions/calendar.php` and `functions/users.php` for the parts that intersect (public event visibility, legacy GF role sync).

**Open findings from this pass (not yet fixed, reported to the orchestrating agent for triage):**
- P1: committee-only calendar (`templates/calendar-committee.php`, backed by `functions/calendar.php`'s `law_calendar_is_committee()`) has NO code-level capability check — access is 100% delegated to the Members plugin's page-level restriction. Every other privileged view in the module (`parts/events/thread.php`, the committee action handler, etc.) has an explicit `law_user_is_committee()`/`law_user_can_manage_event()` check as defence in depth; this one doesn't. If that page's Members restriction is ever misconfigured or removed, all non-draft event statuses (proposed/sent-back/approved/rejected/confirmed) become visible to any visitor who can load the page.
- P1: co-owner email-match auto-link grants event-management access to an existing third-party account with no consent step (see `[[recurring-patterns]]` for the mechanism). Re-runs on every post-approval host edit, not just once.
- P2: `law_speaker_upsert()` email-match backfill lets a host attach unverified bio/job_title/organisation/photo to a genuine, unrelated person's shared public speaker profile (see `[[recurring-patterns]]`).
- P2: `law_migration_create_snapshot()` (`migration/runner.php`) shells out to `mysqldump ... -p<password>`, which exposes `DB_PASSWORD` in the process list (`ps aux`) for the duration of the dump on any multi-tenant/shared host. Low likelihood on typical single-tenant WP hosting, but a one-line fix (`MYSQL_PWD` env var or `--defaults-extra-file`) removes it entirely.
- P2 (suspected, not reproduced live): Stripe webhook idempotency (`law_stripe_processed_events` option, `stripe/webhook.php`) is read-then-write on a single option with no locking — two near-simultaneous deliveries of the same event ID could both pass the dedupe check before either writes, causing a duplicate `confirm` transition / duplicate emails. Requires genuinely concurrent webhook delivery to trigger; Stripe retries are normally sequential, so this is a theoretical race, not a demonstrated one.

**Confirmed clean / re-verified in this pass (don't re-litigate unless the code changes):**
- Workflow engine (`workflow.php`): the `wp_insert_post_data` status guard, the `who`/`from` transition guards, and the `is_machine` bypass (scoped to `stripe_webhook`/`migration`/`system` sources) are all correctly shaped. No path lets a host self-approve, skip a state, or un-reject.
- `meta.php`'s single sanitiser schema is used by BOTH the front-end form (`submission-form.php`) and the wp-admin meta boxes (`admin/event-screen.php`, `speaker-screen.php`, `session-screen.php`) — no meta key found with a second, weaker write path.
- `_law_fee_pence` is never writable from any host-facing input; it's only ever set by `law_event_snapshot_fee()` at approval. Committee-only fields (`_law_fee_override`, `_law_fee_override_amount`, `_law_assignee`, `_law_slot_label`) are only reachable from handlers gated by `law_user_is_committee()`.
- Stripe webhook (`stripe/webhook.php`): raw body read before `json_decode`, `hash_equals()` signature comparison, 300s replay tolerance, idempotency store checked before dispatch. Amount mismatches on `invoice.paid` are logged/alerted but don't block confirmation (documented decision, not a bug).
- Migration snapshot exposure gate (`migration/runner.php`): random 32-char filename suffix, `.htaccess` deny + `index.php`, AND a live unauthenticated-GET self-test that deletes the file and fails closed if the server actually serves it. This is a strong, verified implementation of the §3.11-adjacent snapshot requirement — don't re-flag the theoretical nginx-ignores-.htaccess risk, the self-test already covers it.
- Migration AJAX runner (`wp_ajax_law_migration_run`) and all snapshot/report download `admin_post_*` handlers: `manage_options` + nonce on every one, plus a `law_migration_lock` transient preventing concurrent step runs.
- GF form deactivation on source cutover (`migration/page.php`) genuinely closes the "GF REST API still accepts submissions on an inactive form" risk its own code comment raises — verified against `GFAPI::submit_form()` in the actual plugin source, which refuses inactive forms.
- Comment/log types (`law_event_comment`, `law_event_log`) are excluded from `comments_clauses` and `comment_feed_where` for any query that isn't the module's own; there's no `register_rest_route` exposing them, and `show_in_rest` is `false` on both `law_event`/`law_speaker`/`law_session` CPTs and all four taxonomies, so there's no REST leak of custom-status posts or internal comment types.
- All three activity-log/thread render points (host view via `parts/events/thread.php`, the same part reused for committee context, and the wp-admin meta box in `admin/event-screen.php`) escape consistently: `wp_kses_post( wpautop( ... ) )` for comment/log bodies, `esc_html()` for names/dates/status labels.
- Honeypot + per-IP-and-per-user rate limiting present and correctly ordered (capability/ownership check → honeypot → rate limit → action) on every public write surface checked: submission form, comment reply, registration, profile update.
- Speaker photo upload (`law_events_validate_photos()` in `submission-form.php`): server-side MIME check via `wp_check_filetype_and_ext()` (not trusting client-supplied type), 5 MB cap, and pixel-dimension bounds (50×50 to 6000×6000) against decompression-bomb-style images — matches the §3.11 upload-hardening requirement.
- No hardcoded Stripe/API secrets found anywhere in the module; both `LAW_STRIPE_SECRET_KEY` and `LAW_STRIPE_WEBHOOK_SECRET` are read exclusively from wp-config constants (`stripe/client.php`).

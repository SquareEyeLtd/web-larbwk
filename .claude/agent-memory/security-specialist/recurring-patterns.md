**Pattern to keep checking: account-detail changes without step-up auth.** As of 2026-09-04 `law_profile_handler()` in `functions/events/registration.php` DOES require the current password for both the password change AND the email change (the email branch added a `wp_check_password()` gate, closing what was previously an open P1). Keep checking this pattern on any future self-service account-management code (phase E/F additions): does changing a security-relevant field (email, roles, 2FA if ever added) require re-authentication, or does the session alone suffice? `wp_update_user()` called directly (not through wp-admin's `user-edit.php`) skips WP core's built-in "confirm new email via link" flow entirely, so custom front-end account code is easy to leave weaker than wp-admin's own equivalent screen — this module got it right, but don't assume new code will by default.

**Pattern that's solid, use as the reference implementation:** the self-service role whitelist in `registration.php` (`law_registration_roles()` → sponsor/event_host/attendee only) is enforced twice independently — once via `array_intersect()` at the point input is read, and again via `law_registration_sync_roles()` only ever looping over that same fixed list when applying add/remove. Any new role-bearing input in this module should follow this double-guard shape, not a single filter point.

**False positive to avoid re-flagging:** WordPress nonces for logged-out visitors are not unique per visitor (no session token to salt with when `is_user_logged_in()` is false), so the same `law_register` nonce value works for any anonymous visitor in the same ~12-24h tick window. This is standard WP behaviour, not a defect in this codebase — the actual defence on that surface is the honeypot + per-IP `law_events_rate_limit_ok()` limiter, not nonce uniqueness. Don't flag "nonce is guessable/shared across anonymous users" as a finding on its own; only flag if the rate limiter or honeypot is missing/weak.

**False positive to avoid re-flagging:** the `admin_init` hook in `functions/wordpress.php` that redirects non-admin/editor users out of wp-admin is correctly scoped — it returns early for logged-out users (line ~53) and again for `pagenow === 'admin-post.php'` (line ~62), so it never interferes with any `admin_post_nopriv_*` or `admin_post_*` handler in the events module. Don't flag this hook as a lockout risk unless that scoping changes.

**False positive to avoid re-flagging:** on cutover, `functions/events/migration/page.php`'s source-flip handler calls `GFFormsModel::update_form_active($form_id, 0)` on the legacy module forms (1,2,3,4,5,6,8,9). This DOES close the GF REST API submission bypass the code comment worries about — verified by reading `GFAPI::submit_form()` → `get_submission_form()` in `wp-content/plugins/gravityforms/includes/api.php`, which explicitly checks `$form['is_active']` and refuses inactive forms before any processing. Don't re-flag "inactive forms are still submittable via /gf/v2/forms/<id>/submissions" as a live vuln; it was checked against the actual GF source, not assumed.

**Fixed 2026-09-05, pattern to keep checking: workflow.php's 'system'-who guard used to let ANY committee user through, not just machine sources.** `law_event_workflow_transition()`'s guard block (the `if ( ! $is_machine ) { ... }` section) had `if ( 'system' === $config['who'] && ! law_user_is_committee( $actor ) )` — the `&& ! law_user_is_committee()` meant a committee user (not just a trusted machine source) could trigger a 'system'-only transition (i.e. `confirm`) directly. This was the actual root cause behind "confirm was reachable from the committee dashboard POST" (EVENTS_4.1_FUNC_V2.md §6, fixed there with an action whitelist in `law_committee_action_handler()`), but the same root guard also left `confirm` reachable via `functions/events/admin/event-screen.php`'s `law_workflow_action` field (no whitelist there), completely unaffected by the committee.php fix. Closed 2026-09-05 by making the 'system' branch unconditional (`if ( 'system' === $config['who'] )`, no committee escape hatch) so only genuinely machine-sourced calls (`stripe_webhook`/`migration`/`system` in `$args['source']`) can ever complete a 'system' transition, regardless of who is logged in. **Check this on every future review of `workflow.php`**: a 'who' guard that special-cases "unless this human happens to hold capability X" instead of checking the trusted `$source` is the same class of bug — any new 'system'-only action must be gated on `$is_machine` alone, never on the actor's role. Also re-check any OTHER admin_post/AJAX/meta-box handler that calls `law_event_workflow_transition()` with a user-suppliable `$action` for a matching front-end-only whitelist (comments.php's resubmit path and submission-form.php's submit/resubmit calls pass hardcoded actions, not user input, so they were never at risk — only committee.php's and admin/event-screen.php's handlers took the action key from `$_POST`).

**Pattern to check on every future review: does a request-supplied status/filter value let a privileged-but-not-fully-trusted role (committee) select a post status that's meant to be MORE restricted than their role, not less?** Found 2026-09-07 in `law_committee_events()` (`committee.php:19-24`, used by the dashboard list and, since 2026-09-07, by `export.php`'s CSV/XLSX/JSON export): the function whitelists "is this a known status key" but doesn't separately ask "is the CURRENT USER allowed to filter to this specific status" — so `?law_status=law-draft` (a known key) returns every host's draft events, even though the module's own visibility rule makes `law-draft` owner-only (stricter than the other non-public statuses, which are host+committee). The UI never offers `law-draft` as a filter option and a sibling function (`law_committee_status_counts()`) explicitly excludes it, so the gap is inconsistency, not intent. Check any new list/filter/export endpoint in this module for the same shape: a status/visibility enum validated only against "is this a real value" rather than "is this a value the current role may request".

**Pattern to check on every future review: does a host-facing action grant DATA ACCESS to an arbitrary third party via an unverified identifier (usually email)?** Two instances found 2026-09-04, both still open (see the phase B review memory): (1) `law_event_ensure_co_owner_users()` in `co-owners.php` links any EXISTING user account matched by email to co-owner status with no consent step, and `law_user_can_manage_event()` treats co-owners exactly like the author — so a host who knows (or guesses) another user's email can grant that stranger edit/view rights over their event, and it re-runs on every host edit after approval, not just once at approval. (2) `law_speaker_upsert()` in `speakers.php` matches an existing `law_speaker` post by email and then backfills any of its currently-EMPTY fields (bio, job_title, organisation, photo) from whatever a submitting host typed — so a host who knows a real speaker's email can attach unverified biographical content or a photo to that speaker's shared, publicly-visible profile. Watch for this same shape (identifier-based match → auto-link/auto-write onto someone else's record) in any new repeater or lookup-by-email feature.

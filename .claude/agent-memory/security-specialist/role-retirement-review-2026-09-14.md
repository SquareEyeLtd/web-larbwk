Reviewed 2026-09-14 against `ROLES_AND_ACCOUNT_HUB.md` (the handoff spec for this work, written same day). Client-directed widening: `event_host`, `sponsor`, `attendee` retired, everyone becomes plain `subscriber`, any signed-in user may submit an event or book a place. Result: PASS, zero P0/P1. Two P3s only (stale docblock in `co-owners.php:15` still says co-owners are created as `event_host` when the code now defaults to `subscriber`; `law_events_create_host_user()`'s `$args['role']` override has no internal whitelist, though no current caller passes it from request data).

**Why it came back clean, worth reusing as the reference shape for any future role-simplification PR:**
- Only two real gates existed on the roles at all (confirmed via `wp_user_roles` — the three roles held only `read`): `law_events_user_can_submit()` (`functions/events/submission-form.php`) and `law_account_user_is_host_like()` (`functions/account-bookings.php`). Both were rewritten to trivial `is_user_logged_in()`/`$user->exists()` checks and kept as named seams rather than inlined, so a future narrowing has one place to go.
- The registration handler (`functions/events/registration.php`) hardcodes `'role' => 'subscriber'` at `wp_insert_user()` time and never reads a role from `$_POST`; the replacement `law_intent` meta is whitelisted via `array_intersect()` at both read (`law_registration_read_intent()`) and write (`law_registration_write_intent()`), which are the ONLY paths that touch that meta key — no second looser write path.
- `law_user_can_manage_event()` (the real ownership gate) was untouched and unaffected by the role change, and every event-scoped view reachable via a GET-param event ID (`?law_thread=`, `?law_event_bookings=`, `?law_event=`) independently re-checks it in the PART itself (`parts/events/thread.php:15`, `parts/events/booking-list.php:50-51`, `templates/account-event-form.php:16`), not just in the listing template that links to them — this is the right shape: the template that assembles a list of your own things doesn't need to re-check ownership, but any endpoint reachable by a bare ID in the query string does, independently, every time.
- Migration step 11 (`law_migration_retire_user_roles()`, `functions/events/migration/runner.php:1930`) is the correct shape for a destructive bulk role change: `add_role('subscriber')` BEFORE any `remove_role()` (so an interrupted run never leaves an account role-less), never `set_role()` (would demote the two live administrator+legacy-role accounts), idempotent by construction (query excludes already-processed accounts rather than a processed flag), and gated by `manage_options` + nonce + fresh-snapshot + passing-preflight (`law_migration_run_step()`, same file, :2096-2108) before any real (non-dry) run.
- `law_icon()` (`functions/helpers.php`) and the new account-hub tiles: confirmed every `icon` value passed to it originates from hardcoded string literals in `header-nav.php`, never from request data or post meta, so the `phpcs:ignore` on its raw-SVG-echo call site (`parts/layout/account-tiles.php:66`) is justified, not a gap.
- `law_auth_redirect_to()` (`functions/auth.php`) still runs everything through `wp_validate_redirect()` (same-host only) before falling back to the new `law_auth_default_redirect()` — no open-redirect regression from adding the new default.

**Dormant-but-live code noted, not flagged as new**: `functions/users.php:8-41` and `:96-129` (legacy `gform_user_registered`/`gform_user_updated` hooks that `add_role()`/`remove_role()` the three retired roles from GF forms 1/3 field values) still exist unchanged and are whitelisted to only those three roles — never privileged ones — but are unreachable while forms 1/3 stay deactivated (GFAPI refuses submission to inactive forms, per [[recurring-patterns]]'s GF-inactive-form entry). `ROLES_AND_ACCOUNT_HUB.md` §2.4 already earmarks these for the post-cutover cleanup ticket; flagged to Denis as informational only, not blocking.

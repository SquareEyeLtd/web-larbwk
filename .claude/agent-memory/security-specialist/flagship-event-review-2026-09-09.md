Reviewed 2026-09-09, branch `events-4.2`, against `FLAGSHIP_UI.md`. **Verdict: PASS**, zero P0/P1, three P3 notes only. This was a well-built feature — worth naming as a reference implementation of the ownership/nonce/validation-before-write/escaping shape for any future admin-POST-handler review in this module.

**What was verified clean (don't re-litigate unless the code changes):**
- `law_flagship_screen()`: `edit_law_events` cap check + `check_admin_referer('law_flagship_save','law_flagship_nonce')` both present and correctly ordered before any write; PRG on success.
- `law_flagship_input_from_post()`: exactly one `wp_unslash()` (recursive, on the whole `$_POST['law_flagship']` array), never re-unslashed per field. Every scalar sanitised by type (`sanitize_text_field`, `law_rich_text_sanitize`, `law_events_sanitize_value(..., 'date'|'time')`, `absint`, `sanitize_email`, `esc_url_raw`, `law_speaker_role_key`).
- `law_flagship_save_sessions()`: a posted session `id` is honoured ONLY when `in_array($posted, $owned, true)` where `$owned = law_event_session_ids($event_id)` — a forged/foreign session ID cannot be hijacked into the flagship, mirrors `law_events_form_save_sessions()`'s ownership rule exactly. `wp_delete_post()` orphan cleanup only ever operates on `array_diff($owned, $kept)`, so it can never touch a session outside the flagship's own tree.
- `law_flagship_validate()` refuses a stale/forged `speaker_id` (`get_post_type($id) !== LAW_SPEAKER_CPT`) rather than silently dropping it, and runs to completion BEFORE `law_flagship_save()` touches anything — a failed validation writes nothing.
- `workflow.php`'s `$GLOBALS['law_flagship_saving']` exemption (`workflow.php:107-111`): scoped to `LAW_EVENT_CPT` + `law_flagship_is($post_id)` + status whitelist (`publish`/`law-draft` only); the global is set and unset around a single synchronous `wp_update_post()` call in `law_flagship_save()` with no early return between set/unset, so it cannot leak across requests or affect any other post.
- `bookings.php`: `law_booking_guard_open()` refuses the flagship explicitly (`bookings.php:387-389`), and it's confirmed the ONLY guard function, called first in all four write paths (`law_booking_create`, `law_booking_add_attendee`, and their re-checks after the lock) — hiding the booking control on the flagship page is genuinely backed by a server-side refusal.
- `fields.php`'s new `render_row`/`after_list` args on `law_field_relationship()`: both call sites in `flagship-screen.php` pass static strings/closures, no interpolated user data reaches `after_list`'s unescaped echo. `law_field_relationship_photo()` correctly keeps `$i`/`$j` as a string (never casts to int), which matters because the flagship's new-speaker template row uses the literal placeholder `__j__`.
- Escaping: every new front-end part (`flagship-card.php`, `session-timeline.php`, `event-venue.php`) and the admin screen's own renderer consistently use `esc_html`/`esc_attr`/`esc_url` on all dynamic output; rich text goes through `wp_kses_post(wpautop(...))`. `functions/events/rich-text.php`'s `law_rich_text_sanitize()` strips `<script>`/`<style>` BLOCKS (contents and all, not just tags) before `wp_kses()`, closing the "tag removed, payload left as visible text" gap.
- `_law_is_flagship` cannot be set from the host form: `submission-form.php` has zero references to it; `law_events_form_save()` writes a fixed key map only.
- All exclusions (`committee.php`'s `law_committee_events()`/`_status_counts()`/`_requested_event()`, `account-events.php`'s CPT loop) use a hardcoded ID comparison (`law_flagship_is()`/`post__not_in`), not a query param — not bypassable by `?law_status=`-style tricks (cf. the [[recurring-patterns]] status-filter pattern).
- `setup-account-pages.php` (`manage_options` + own admin_init gate) and `migration/runner.php` (`manage_options` in `law_migration_run_step()`, snapshot-lock, dry-run) both call `law_flagship_ensure_post()` from inside their existing gates — no new unauthenticated path.
- Traced the specific claim in `templates/flagship-event.php` ("anonymous request for an unpublished event 404s before the template runs"): confirmed via WP core's `register_post_status(..., 'protected' => true)` semantics (`statuses.php:69-86`, all custom statuses registered `public => false`, `protected => true`) combined with `map_meta_cap => true` + `capability_type => ['law_event','law_events']` (`post-types.php:19-22`). WP_Query only includes protected statuses in a front-end singular/preview query for a user who holds the post type's `edit_post` meta cap on that specific post; a plain visitor has neither `edit_law_events` (own post) nor `edit_others_law_events` (committee), so the row is excluded at the SQL level and the request 404s — `template_include`'s `law_flagship_is(get_queried_object_id())` check never fires because there's no queried object. This applies identically to `?post_type=law_event&p=<id>` (same status-inclusion gate, different query var) and to feeds/search (both fall back to the public-status-only default plus the CPT's own `exclude_from_search => true`). Reasoning holds. The in-template `current_user_can('edit_post', id)` branch is genuine defence in depth, not the only lock, exactly as its own comment claims.
- Traced `law_calendar_flagship_event()`'s own doc comment claim that a draft flagship "renders (with its status badge) for the committee" — this is actually WRONG as written (see P3 note below), but the code is safe either way: `law_events_map_post()`'s `if ('law-draft' === $post->post_status && !$with_drafts) return null;` fires for the committee context too (`law_calendar_event_by_id()` passes `array()`, not `array('*')`, so `$with_drafts` is false there), so a draft flagship is excluded from BOTH the public and committee calendar, same as any other host's draft event. No leak through the committee calendar (a route this module's own memory already flags as having no code-level cap check, [[phase-b-hostile-review-2026-09-04]]) — the flagship does not widen that pre-existing hole, because its draft state never reaches that view.

**P3 notes (not vulnerabilities, worth a follow-up ticket, not blocking):**
1. `functions/calendar.php:988-995` — the doc comment above `law_calendar_flagship_event()` says a draft flagship "renders (with its status badge) for the committee," but tracing `law_events_map_post()` shows it actually returns `null` there too (see above) — the code is stricter/safer than documented, but a future maintainer reading the comment could reasonably assume the committee calendar is where they'd preview a draft flagship (it isn't; that's the Flagship screen itself), and the manual acceptance checklist (FLAGSHIP_UI.md §8 step 5) only exercises the committee calendar AFTER step 2 already published the fixture, so this discrepancy isn't caught by the documented QA pass either.
2. No automated test pins "an anonymous GET to `/events/flagship/` (or `?post_type=law_event&p=<id>`) while the flagship is `law-draft` returns 404." The property is real today but depends entirely on WP core's `protected` post-status + `map_meta_cap` behaviour, which nothing in this codebase asserts directly — a future change to `law_events_capability_args()`, a `map_meta_cap`-disabling edit, or a broad `user_has_cap` filter from another plugin could silently reopen it with no test failing. Worth a `FlagshipRenderTest` case doing a real anonymous `WP_Query`/`template_include` pass against a draft fixture (the existing test plan's `test_template_include_routes_the_flagship_to_its_own_template` covers routing but not the visibility gate itself).
3. `law_field_relationship()`'s new `$args['after_list']` (fields.php:186-188) is documented "caller-escaped" but there's no assertion/escaping at the call site — both of today's two callers pass static strings, so it's safe now, but the pattern is one bad future caller away from an admin-context XSS if someone ever interpolates a title or search term into it without `esc_html`.

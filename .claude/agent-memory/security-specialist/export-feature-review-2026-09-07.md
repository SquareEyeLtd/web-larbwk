Reviewed `functions/events/export.php` (new), `functions/events/committee.php`'s new `$overrides` param on `law_committee_events()`, `functions/events/source.php`'s `law_event_sector_summary()`, `templates/account-dashboard.php` export buttons markup, `assets/js/export-buttons.js`, and vendored pdfmake 0.2.12.

**Open finding (P2, per the standing checklist's own "Draft leakage" bucket, not escalated):** `law_committee_events()` (`committee.php:19-24`) takes `$_GET['law_status']` and, whenever it's a *known* status key, uses it verbatim as the query's `post_status` with no further scoping. `law-draft` IS a known key (`statuses.php:16`), so `?law_status=law-draft` returns every host's draft events, not just the querying user's own — violating the module's own rule that draft is owner-only (stricter than the other non-public statuses, which are host+committee). The dashboard `<select>` never offers `law-draft` as an option and `law_committee_status_counts()` explicitly excludes it, so this is clearly unintended, just not blocked server-side. `export.php:78` calls the same function with `posts_per_page => -1`, turning a capped (300-row) on-screen leak into a full unfiltered CSV/XLSX/JSON/PDF dump of every host's unsubmitted draft data (names, emails, titles) in one request. Reachable only by an already-authenticated committee/admin account (capability check on the export endpoint is otherwise sound), so this is an internal-trust-boundary violation, not an external one. Fix direction: in `law_committee_events()`, treat `law-draft` as never a valid explicit filter value (fall through to the existing `array_diff(..., array('law-draft'))` default), same way the status-counts and filter-dropdown code already special-case it. Also check `law_committee_requested_event()` (same file, single-event `?event=` lookup) separately — it has no status check at all, so a committee user browsing directly to another host's draft's `?event=<id>` detail view may hit the same underlying "committee can see drafts" gap via a different vector; not confirmed against the template's rendering logic, worth a follow-up look.

**Confirmed clean, don't re-litigate:**
- No `admin_post_nopriv_law_committee_export` registered (grepped the whole theme); capability (`law_user_is_committee()`) is checked independently of nonce validity, so a leaked/forged nonce alone can't grant access.
- `$overrides` param on `law_committee_events()`: only two call sites in the whole codebase (`parts/events/dashboard-list.php` passes none; `export.php:78` passes a hardcoded literal `array('posts_per_page' => -1)`). No attacker-influenced override reachable.
- CSV formula-injection guard (`law_events_csv_guard`) matches OWASP's `=+-@\t\r` first-character set and is applied via `array_map` across every column, not just suspect ones.
- XLSX writer uses `t="inlineStr"` (typed text), which is structurally immune to formula injection regardless of leading character — correctly NOT reusing the CSV guard function for XLSX, since the risk classes differ. XML escaping (`law_events_xml_text()`) strips disallowed C0 controls (keeping tab/LF/CR) and `htmlspecialchars(ENT_XML1|ENT_QUOTES)`-escapes the rest. Filename in `Content-Disposition` is 100% server-generated (static prefix + `gmdate()`), no request data reaches it.
- pdfmake 0.2.12 usage is client-side only, with a developer-authored `docDefinition` and only plain-text leaf values from a same-origin JSON fetch — no attacker path to the `docDefinition` structure itself. Checked Snyk: CVE-2024-25180 was formally revoked ("doesn't affect any version of package pdfmake"); CVE-2022-46161/GHSL-2022-068 is specific to a server-side demo `/pdf` endpoint accepting raw client-supplied docDefinitions, not applicable to this client-side-only usage. No CVE found that applies here.
- `nocache_headers()` covers all three success branches (CSV/XLSX/JSON) — called once before the format `if` blocks. It does NOT cover the two earlier 403 branches (bad nonce / non-committee), but those carry no PII, so this is a P3 defence-in-depth note at most, not a real gap.
- Minor P3s recorded (not escalated): `law_events_send_xlsx()` doesn't `unlink()` the `wp_tempnam()` file if `ZipArchive::open()` fails (the `wp_die()` on that branch skips cleanup) — a reliability/hygiene gap, not a demonstrated exposure, since the file only exists within one request and (on typical WP setups) `get_temp_dir()` resolves outside the webroot; the `wp_enqueue_scripts` callback loads the ~3MB pdfmake bundle for any visitor of the dashboard template regardless of committee status (gated only by `is_page_template()`), wasteful but not a disclosure since `export-buttons.js` no-ops when it finds no `[data-law-export]` node.

See [[recurring-patterns]] for the reusable pattern this review added (request-supplied status/filter values selecting a status more restricted than the querying role should see).

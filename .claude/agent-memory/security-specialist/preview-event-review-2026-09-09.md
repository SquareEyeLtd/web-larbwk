Reviewed 2026-09-09: new `/account/dashboard/?preview-event=<id>` route letting committee preview an unpublished event through the attendee-facing single-event renderer (`parts/calendar-body.php`). Files: `templates/account-dashboard.php:11-39`, `parts/calendar-body.php` (new `$law_cal_event`/`$law_cal_back` caller-set variables).

**Open findings:**
- P2: the primary template render (`templates/account-dashboard.php`, including the preview branch) never calls `nocache_headers()`. Sibling AJAX partial endpoints on the same page (`law_committee_maybe_render_partial()` in `functions/events/committee.php:87`, and `functions/calendar.php:250`) already do this for their own JSON/partial responses, so the omission on the main page render is inconsistent, not a deliberate decision. If any host-level cache/CDN in front of PHP caches by URL regardless of auth cookies, a cached hit could serve unpublished-event HTML to a later anonymous request at the exact same URL. Not exploitable against this repo's own stack (no page-cache plugin installed), but worth closing since production infra is outside the repo's visibility (same caveat class as the migration-snapshot `.htaccess`-on-nginx gap from the phase B review).
- P3 (hardening, not exploitable today): `law_events_map_post( $id, array() )` treats "all statuses" as "every post_status except `law-draft`", which silently includes `trash` and any future/unregistered status, not just the six `law_event_statuses()` moderation states the preview is meant to unlock. Since only committee/editor/admin can ever reach this branch (`law_user_is_committee()` gates it before anything else runs), this is not a real leak, just a scope-creep risk if the preview gate is ever loosened later. Suggest whitelisting explicitly: `array_diff( law_event_all_status_keys(), array( 'law-draft' ) )`.

**Confirmed clean (don't re-litigate):**
- `law_user_is_committee()` (wraps `user_can( ..., 'edit_others_law_events' )`, granted only to administrator/editor/events_committee via `law_events_grant_capabilities()`) correctly gates the whole preview branch before any Members check runs, so a signed-out visitor/attendee/host/sponsor/subscriber cannot reach it even if Members is misconfigured or deactivated.
- The `$calendar_blocked` (Members) layering in `parts/calendar-body.php:40-46` cannot be inverted: when Members blocks the page, `$event` stays null regardless of `$law_cal_event`, and the Members error message renders (lines 119-122).
- `law_events_map_post()`'s post-type check (`functions/events/source.php:52`) safely rejects a `$law_preview_id` naming a page, attachment, revision or `law_booking` post before any status logic runs.
- The hydrate/render pipeline for the preview (`law_events_cpt_hydrate()`, `parts/events/speaker-card.php`, `parts/calendar-event-details.php`) only ever prints attendee-facing fields (title, description, venue, sessions, speaker name/bio/photo/role). None of invoice/fee/VAT/co-owner-email/contact/activity-log data (which the committee's own detail view further down the same template *does* render) leaks into this branch.
- `law_booking_render_action()` (`functions/account-bookings.php:229`) returns early with no output for any non-`publish` post, so the preview never shows booking-state UI.
- `$law_cal_back_url`/`$law_cal_back_label` are template-scope locals set only by `templates/account-dashboard.php` from `add_query_arg( 'event', absint(...), get_permalink() )` and a translated literal — never from request data — and both are `esc_url()`/`esc_html()`'d at every render site. All four callers of `parts/calendar-body.php` (`templates/calendar.php`, `templates/calendar-committee.php`, `templates/event-single.php`, `templates/account-dashboard.php`) use a plain `require` (shared scope by design), not `get_template_part()` (isolated scope), and no other file in the theme sets these two variables.
- `?preview-event=` is read only via raw `$_GET`, never registered as a query var, so it cannot collide with core's `preview`/`p`/`page_id` preview machinery, nor with the theme's own legacy `?event=` redirect (`functions/events/source.php:467-500`), which is scoped to `is_page_template( 'templates/calendar.php' )` only.
- `?preview-event[]=` array injection: `absint( wp_unslash( array(...) ) )` collapses to 0 or 1 (PHP's `intval(array)` quirk) — same pre-existing pattern as `law_calendar_requested_event_id()`'s handling of `$_GET['event']`. Not exploitable (worst case resolves to post ID 1, which fails the post-type check).
- No double-render / headers-already-sent risk: the `return` inside the preview branch stops execution before `get_header()`, and `calendar-body.php` supplies its own header/footer pair, so exactly one renders regardless of branch.

2026-09-16: reviewed the change making `law-approved` a public, publicly_queryable, unprotected post status (previously public=false/protected=true), plus the new `_law_booking_override` (auto|disable|enable) committee switch and a `_law_venue` write added to the committee dashboard handler, plus a wp-admin migration repair panel. Zero P0/P1/P2 findings — clean PASS. Full trace, useful as a reference for the next status-visibility or override-switch change:

**Why it's safe, in one sentence each:**
- Public/queryable/unprotected on the STATUS only changes whether a direct single-post visit 404s (WP core's protected-status `map_meta_cap` gate, see [[recurring-patterns]] item on the flagship review) — it does NOT change what `law_calendar_public_statuses()`/`law_events_cpt_mapped_events()` puts in the calendar's own explicit `get_posts( post_status => [...] )` array query, which is a *separate*, independently-maintained allow-list ('Confirmed' only on the legacy GF source, 'Confirmed'+'Approved' on CPT). Both had to change together and did.
- The 'enable' override lifts the `'publish' !== $post->post_status` gate in `law_booking_guard_open()` (bookings.php ~line 1018), but the 'places released' hold (`law_event_booking_hold_reason()`) is checked BEFORE the override is consulted, so Enable booking cannot conjure capacity that was never allocated — confirmed by reading the order of checks, not just the comments.
- `_law_booking_override` and `_law_venue` are each written from exactly two places: the front-end committee dashboard handler (`law_committee_action_handler()`, gated on `law_user_is_committee()` + nonce) and the wp-admin event screen save (`law_event_admin_save()`, gated on `current_user_can('edit_law_events')`, only ever granted to administrator/editor/events_committee — verified in `capabilities.php`). The host-facing `submission-form.php` save path writes `_law_venue` too but through its own explicit `$writes` allow-list array (never a generic loop over the meta schema) and never touches `_law_booking_override` at all. One shared sanitiser (`meta.php`'s `booking_override` case, falls back to `auto` on anything else) applies regardless of which path writes it.
- The wp-admin "Committee controls" panel with the new venue input + override select is gated THREE times over: (1) the whole dashboard template body is behind `if ( ! law_user_is_committee() )` at the top of `account-dashboard.php`, (2) the form posts through `law_committee_action_handler()`'s own `law_user_is_committee()` + nonce check, (3) `edit_law_events` cap on the wp-admin equivalent.
- The migration repair panel (`repair-payment-status.php`) is behind `manage_options` (admin-only) at the *page* level (`law_migration_admin_page()`), and even so re-validates every posted ID against a fresh scan (`law_events_repair_payment_scan()`) before writing — a forged ID that doesn't currently qualify (wrong fee/status/payment combination) is silently skipped rather than written, so there's no arbitrary-post-write even for an admin who fat-fingers a request.
- Every booking-creation entry point (`law_booking_create_handler`, waitlist join, register-on-behalf, the reception checkout, the `?law_dialog=1` fragment server) funnels through the same two functions (`law_booking_guard_open()` / `law_booking_guard_form_open()`), confirmed by grep across the whole `functions/` tree — no parallel bypass path exists.
- `law-event` CPT already had `show_in_rest => false` before this change, so the new public status does not open any REST exposure; sitemap generation (SEOPress) and the main query both key off `post_status=publish` explicitly and are unaffected by a status's own `public` flag.

**Watch for next time:** if a future change adds a THIRD public status, or widens `law_calendar_public_statuses()` again, re-verify the same two-part pairing (label allow-list AND status registration) moves together — it's an easy place for the two to drift since they live in different files (`calendar.php` vs `statuses.php`).
